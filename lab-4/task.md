# Задание для агента: Лабораторная работа № 4 — переводчик арифметических выражений в ОПЗ на базе МП-преобразователя

## 1. Роль и цель

Реализовать переводчик арифметических выражений (операции `+`, `-`, `*`, `/`, целые числа) в обратную польскую запись (ОПЗ). Реализация должна строго следовать теории перевода, изложенной в главе 4 «Теория перевода» учебного пособия (ТЯП, гл. 4): работа строится как последовательность «КС-грамматика → простая СУ-схема → детерминированный МП-преобразователь → программа».

## 2. Принятые соглашения и обозначения (по гл. 4 ТЯП)

Все формальные построения в отчёте и в коде оформляются в точности по следующим соглашениям главы 4.

### 2.1. Перевод

- **Перевод** (трансляция) — отношение `T` из `V₁*` в `V₂*`: множество пар `(x, y)`, где `x ∈ V₁*` — входная цепочка, `y ∈ V₂*` — выходная цепочка; `(x, y) ∈ T`, `y` называется **выходом** для входа `x`.
- Перевод для языка программирования должен быть **функцией**: каждому входу — не более одного выхода.
- Устройство, которое по входной цепочке `x` вычисляет `y` такое, что `(x, y) ∈ T`, называется **транслятором**, реализующим перевод `T`.

### 2.2. СУ-схема (схема синтаксически управляемого перевода / трансляции)

- **СУ-схема** — пятёрка `T = (VN, VT₁, VT₂, R, S)`, где:
  - `VN` — конечное множество нетерминальных символов;
  - `VT₁` — конечный **входной** алфавит; `VT₂` — конечный **выходной** алфавит;
  - `S` — целевой символ;
  - `R` — конечное множество правил вида `A → α.β`, где `α ∈ (VN ∪ VT₁)*`, `β ∈ (VN ∪ VT₂)*`. Вхождения нетерминалов в цепочку `β` образуют перестановку вхождений нетерминалов в цепочку `α` (каждому вхождению нетерминала в `α` соответствует вхождение того же нетерминала в `β`).
- Правила записываются **через точку**: входная часть `.` выходная часть (пример: `S → 0S.aaSbb`). Пустая цепочка обозначается `λ`.
- **Выводимая пара цепочек**: (1) `(S, S)` — выводимая пара; (2) если `(αAβ, α'Aβ')` — выводимая пара и `A → γ.γ'` — правило из `R`, то `(αγβ, αγ'β')` — выводимая пара.
- **Перевод, определяемый схемой `T`**: `τ(T) = { (x, y) | (S, S) ⇒* (x, y), x ∈ VT₁*, y ∈ VT₂* }`. Если `T` — СУ-схема, то `τ(T)` называется **СУ-переводом**.
- **Входная грамматика** СУ-схемы `T`: `G(VN, VT₁, P, S)`, где `P = { A → α | (A → α.β) ∈ R }`. **Выходная грамматика**: `G'(VN, VT₂, P', S)`, где `P' = { A → β | (A → α.β) ∈ R }`.
- СУ-схема называется **простой**, если для любого правила `(A → α.β) ∈ R` соответствующие друг другу вхождения нетерминалов встречаются в `α` и `β` **в одном и том же порядке**. Перевод простой СУ-схемы — **простой СУ-перевод**. Простые СУ-схемы образуют важный класс: для них легко построить транслирующий МП-преобразователь.

### 2.3. Конечный преобразователь (для справки, в работе не реализуется)

- Шестёрка `M = (Q, VT₁, VT₂, δ, q₀, F)`; такт: `(q, ax, y) ⊢ (q', x, yz)`, если `δ(q, a)` содержит `(q', z)`.
- Выход для цепочки `x`: `(q₀, x, λ) ⊢* (q, λ, y)` для некоторого заключительного состояния `q ∈ F`. Перевод: `τ(M) = { (x, y) | x ∈ VT₁*, y ∈ VT₂*, ∃q ∈ F: (q₀, x, λ) ⊢* (q, λ, y) }`.

### 2.4. МП-преобразователь (преобразователь с магазинной памятью)

- **МП-преобразователь** — восьмёрка `P = (Q, V, Z, V', δ, q₀, z₀, F)`, где относительно обычного МП-автомата добавлен выходной алфавит `V'`, а функция переходов действует из `Q × (V ∪ {λ}) × Z` в `Q × Z* × V'`. Остальные компоненты имеют тот же смысл, что и в МП-автомате: `Q` — состояния, `V` — входной алфавит, `Z` — алфавит магазина (стека), `V'` — выходной алфавит, `q₀` — начальное состояние, `z₀` — начальный символ магазина, `F` — множество заключительных состояний.
- **Конфигурация** — четвёрка `(q, x, α, y)`, где `q` — состояние, `x` — непрочитанная часть входной цепочки, `α` — содержимое магазина, `y` — выходная цепочка, выданная к настоящему моменту.
- **Такт работы**: если `δ(q, a, z)` содержит `(r, α, t)`, то `(q, ax, zγ, y) ⊢ (r, x, αγ, yt)` для всех `x ∈ V*`, `a ∈ V ∪ {λ}`, `z, γ ∈ Z*`, `y, t ∈ V'`.
- **Выход для цепочки `x`**: `(q₀, x, z₀, λ) ⊢* (q, λ, α, y)` для некоторого `q ∈ F` и `α ∈ Z*`.
- **Перевод, определяемый преобразователем `P`**: `τ(P) = { (x, y) | x ∈ V*, y ∈ V*, ∃q ∈ F, ∃α ∈ Z*: (q₀, x, z₀, λ) ⊢* (q, λ, α, y) }`.
- Правила переходов записываются в виде: `δ(q, a, z) = { (r, α, t) }` — из состояния `q` при чтении входного символа `a` (или `λ`) с верхушкой магазина `z` перейти в состояние `r`, заменить `z` на цепочку `α` в магазине и выдать цепочку `t` на выходную ленту.
- Обязательные элементы описания любого перевода в отчёте: (1) формальная спецификация СУ-схемы/преобразователя со всеми компонентами; (2) такт работы (`⊢`); (3) разбор (последовательность конфигураций) хотя бы одного контрольного примера.

## 3. Предметное задание (по файлу «Лабораторная работа № 4»)

### Этап 1. КС-грамматика и простая СУ-схема

1. Составить **КС-грамматику** для заданных арифметических выражений: операции `+`, `-`, `*`, `/`, целые числа, скобки. Грамматика должна задавать правильный приоритет операций (`*`, `/` выше, чем `+`, `-`) и левоассоциативность.
2. На её основе разработать **простую СУ-схему** для перевода в ОПЗ. Форма записи правил: `A → α.β` (входная часть, точка, выходная часть).
3. **Выходные символы — терминалы `(num, +, -, *, /)` и пробелы**: числа переносятся в выходную ленту как лексемы `num`, операции — как свои символы, лексемы разделяются пробелами. Пример: вход `5 + 3* 2` → выход `5 3 * 2 +`.

### Этап 2. Построение МП-преобразователя

Для СУ-схемы перевода в ОПЗ построить **формальную спецификацию детерминированного МП-преобразователя**:

- определить множество состояний `Q`, входной алфавит `V`, алфавит магазина `Z`, выходной алфавит `V'`, начальное состояние `q₀`, начальный символ магазина `z₀`, множество заключительных состояний `F`;
- главное — определить **функцию переходов** `δ` (полный набор правил `δ(q, a, z) = {(r, α, t)}`);
- преобразователь должен считывать символы входной строки и записывать символы в выходную строку;
- привести такт работы (`⊢`) и полный разбор контрольного примера `5 + 3* 2` в виде последовательности конфигураций `(q, x, α, y)`.

### Этап 3. Программная реализация МП-преобразователя

Реализовать полученный МП-преобразователь для перевода в ОПЗ в виде программы. Программа должна:

- считывать строку-выражение (например, `5 + 3* 2`);
- посимвольно обрабатывать её, **имитируя работу МП-преобразователя** (состояние, стек, выходная лента);
- выводить получившуюся ОПЗ-строку (для `5 + 3* 2` — `5 3 * 2 +`);
- **корректно обрабатывать ошибки** (недопустимые символы, нарушение синтаксиса, дисбаланс скобок, недопустимые комбинации операций, ошибки конца входа и т.п.) — с локализацией позиции ошибки и понятным сообщением;
- для корректной работы преобразователя **реализовать λ-переходы** (переходы `δ(q, λ, z)`, выполняемые без чтения входного символа; в детерминированном преобразователе λ-переход разрешён только если для данного `q`, `z` нет конфликтующего перехода по реальному входному символу).

## 4. Технологический стек (обязательные требования)

| Требование | Значение |
|---|---|
| Система сборки | Gradle, сборочный скрипт **на Kotlin DSL** (`build.gradle.kts`), wrapper включён |
| Язык | **Java 25** (toolchain / sourceCompatibility = 25) |
| Логирование | **Lombok `@Slf4j`** (SLF4J + бэкенд Logback), логирование шагов работы преобразователя: чтение символа, такт, состояние, стек, выходная лента |
| Тесты | **JUnit 5 + AssertJ + Mockito**; все ключевые сценарии покрыты тестами |
| Запуск | Приложение запускается через **`gradlew.bat`** (для Windows; `gradlew` — для Unix), т.е. `gradlew.bat run` |
| Входные данные | В формате **JSON**, парсинг — **Jackson** (`jackson-databind`) |

Уточнения по стеку:

- Входной JSON — файл (путь передаётся аргументом программы) или stdin, формат минимум: `{ "expression": "5 + 3* 2" }`. Допустимо расширить формат (например, массивом выражений), задокументировав схему в README.
- Результат — ОПЗ-строка — выводится на экран (требование лабораторной); дополнительно можно продублировать результат в JSON-вывод, но консольный вывод ОПЗ обязателен.
- Lombok используется не только для `@Slf4j`, но и для сокращения шаблонного кода (`@Value`, `@Builder`, `@RequiredArgsConstructor` и т.п. — по усмотрению).
- Запуск: `gradlew.bat run --args="path/to/input.json"` (настроить задачу `run` в `build.gradle.kts` через плагин `application`).

## 5. Требования к структуре решения

Рекомендуемая структура пакета (имена можно адаптировать, сохранив разделение ответственности):

1. **Модель преобразователя** — неизменяемое описание `P = (Q, V, Z, V', δ, q₀, z₀, F)`: перечисления состояний и символов магазина, тип `Transition(q, a, z) → (r, α, t)`, таблица переходов.
2. **Движок (интерпретатор) МП-преобразователя** — универсальный такт: по текущей конфигурации `(q, x, α, y)` и правилу из `δ` выполняет шаг `(q, ax, zγ, y) ⊢ (r, x, αγ, yt)`; поддерживает как переходы по чтению символа, так и λ-переходы; детерминирован — при неоднозначности (конфликте правил) сообщает об ошибке.
3. **Спецификация конкретного преобразователя для ОПЗ** — фактические множества и таблица `δ`, построенная по СУ-схеме из этапа 1.
4. **Ввод/вывод** — чтение JSON через Jackson, вывод ОПЗ и диагностических сообщений.
5. **Обработка ошибок** — свои типы исключений (например, `TranslationException` с позицией символа), понятные сообщения; никакой вход не должен «ронять» программу необработанным исключением.

Порядок работы движка на каждом такте должен соответствовать формальному определению из п. 2.4 (состояние, оставшийся вход, магазин, выходная лента) — это проверяется в тестах.

## 6. Тестирование (обязательное)

- **JUnit 5** как тестовый движок, **AssertJ** для утверждений (`assertThat(...)`), **Mockito** для изоляции зависимостей (например, мок вывода/логики, если движок взаимодействует с IO-компонентами).
- Обязательные группы тестов:
  1. корректные выражения: `5 + 3* 2` → `5 3 * 2 +`; со скобками; все четыре операции; вложенные скобки; многозначные числа; выражение из одного числа;
  2. λ-переходы: сценарии, где такт выполняется без чтения символа (завершающие операции над стеком при конце входа);
  3. ошибки: недопустимый символ, `5 + * 3`, `5 +` (нехватка операнда), `(5 + 3` (дисбаланс скобок), `5 3 +` (недопустимая последовательность), пустая строка; проверяются код/сообщение и позиция ошибки;
  4. детерминированность и корректность такта: последовательности конфигураций для контрольного примера совпадают с ручным разбором из этапа 2;
  5. парсинг JSON (Jackson): корректный файл, некорректный JSON, отсутствие поля `expression`.
- В тестах использовать параметрылизацию (`@ParameterizedTest`) для перебора выражений «вход → ожидаемая ОПЗ».
