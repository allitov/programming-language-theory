# Задание для агента: Лабораторная работа № 4 — переводчик арифметических выражений в ОПЗ на базе универсального МП-преобразователя

## 1. Роль и цель

Реализовать переводчик арифметических выражений (операции `+`, `-`, `*`, `/`, целые числа) в обратную польскую запись
(ОПЗ). Работа строится как последовательность «КС-грамматика → простая СУ-схема → детерминированный
МП-преобразователь → программа». Программа — **универсальный МП-преобразователь**: конфигурация и правила переходов
считываются из json-файла, входные строки-выражения поступают из консольного ввода, каждый такт преобразования
выводится в консоль (формат вывода и структура json — п. 2.5).

## 2. Принятые соглашения и обозначения

Все формальные построения в отчёте и в коде оформляются в точности по следующим соглашениям главы 4.

### 2.1. Перевод

- **Перевод** (трансляция) — отношение `T` из `V₁*` в `V₂*`: множество пар `(x, y)`, где `x ∈ V₁*` — входная цепочка,
  `y ∈ V₂*` — выходная цепочка; `(x, y) ∈ T`, `y` называется **выходом** для входа `x`.
- Перевод для языка программирования должен быть **функцией**: каждому входу — не более одного выхода.
- Устройство, которое по входной цепочке `x` вычисляет `y` такое, что `(x, y) ∈ T`, называется **транслятором**,
  реализующим перевод `T`.

### 2.2. СУ-схема (схема синтаксически управляемого перевода / трансляции)

- **СУ-схема** — пятёрка `T = (VN, VT₁, VT₂, R, S)`, где:
    - `VN` — конечное множество нетерминальных символов;
    - `VT₁` — конечный **входной** алфавит; `VT₂` — конечный **выходной** алфавит;
    - `S` — целевой символ;
    - `R` — конечное множество правил вида `A → α.β`, где `α ∈ (VN ∪ VT₁)*`, `β ∈ (VN ∪ VT₂)*`. Вхождения нетерминалов в
      цепочку `β` образуют перестановку вхождений нетерминалов в цепочку `α` (каждому вхождению нетерминала в `α`
      соответствует вхождение того же нетерминала в `β`).
- Правила записываются **через запятую**: входная часть `,` выходная часть (пример: `S → 0S,aaSbb`). Пустая цепочка
  обозначается `λ`.
- **Выводимая пара цепочек**: (1) `(S, S)` — выводимая пара; (2) если `(αAβ, α'Aβ')` — выводимая пара и `A → γ,γ'` —
  правило из `R`, то `(αγβ, αγ'β')` — выводимая пара.
- **Перевод, определяемый схемой `T`**: `τ(T) = { (x, y) | (S, S) ⇒* (x, y), x ∈ VT₁*, y ∈ VT₂* }`. Если `T` — СУ-схема,
  то `τ(T)` называется **СУ-переводом**.
- **Входная грамматика** СУ-схемы `T`: `G(VN, VT₁, P, S)`, где `P = { A → α | (A → α,β) ∈ R }`. **Выходная грамматика**:
  `G'(VN, VT₂, P', S)`, где `P' = { A → β | (A → α,β) ∈ R }`.
- СУ-схема называется **простой**, если для любого правила `(A → α,β) ∈ R` соответствующие друг другу вхождения
  нетерминалов встречаются в `α` и `β` **в одном и том же порядке**. Перевод простой СУ-схемы — **простой СУ-перевод**.
  Простые СУ-схемы образуют важный класс: для них легко построить транслирующий МП-преобразователь.

### 2.3. Конечный преобразователь (для справки, в работе не реализуется)

- Шестёрка `M = (Q, VT₁, VT₂, δ, q₀, F)`; такт: `(q, ax, y) ⊢ (q', x, yz)`, если `δ(q, a)` содержит `(q', z)`.
- Выход для цепочки `x`: `(q₀, x, λ) ⊢* (q, λ, y)` для некоторого заключительного состояния `q ∈ F`. Перевод:
  `τ(M) = { (x, y) | x ∈ VT₁*, y ∈ VT₂*, ∃q ∈ F: (q₀, x, λ) ⊢* (q, λ, y) }`.

### 2.4. МП-преобразователь (преобразователь с магазинной памятью)

- **МП-преобразователь** — восьмёрка `P = (Q, V, Z, V', δ, q₀, z₀, F)`, где относительно обычного МП-автомата добавлен
  выходной алфавит `V'`, а функция переходов действует из `Q × (V ∪ {λ}) × Z` в `Q × Z* × V'`. Остальные компоненты
  имеют тот же смысл, что и в МП-автомате: `Q` — состояния, `V` — входной алфавит, `Z` — алфавит магазина (стека),
  `V'` — выходной алфавит, `q₀` — начальное состояние, `z₀` — начальный символ магазина, `F` — множество заключительных
  состояний.
- **Конфигурация** — четвёрка `(q, x, α, y)`, где `q` — состояние, `x` — непрочитанная часть входной цепочки, `α` —
  содержимое магазина, `y` — выходная цепочка, выданная к настоящему моменту.
- **Такт работы**: если `δ(q, a, z)` содержит `(r, α, t)`, то `(q, ax, zγ, y) ⊢ (r, x, αγ, yt)` для всех `x ∈ V*`,
  `a ∈ V ∪ {λ}`, `z, γ ∈ Z*`, `y, t ∈ V'`.
- **Выход для цепочки `x`**: `(q₀, x, z₀, λ) ⊢* (q, λ, α, y)` для некоторого `q ∈ F` и `α ∈ Z*`.
- **Перевод, определяемый преобразователем `P`**:
  `τ(P) = { (x, y) | x ∈ V*, y ∈ V*, ∃q ∈ F, ∃α ∈ Z*: (q₀, x, z₀, λ) ⊢* (q, λ, α, y) }`.
- Правила переходов записываются в виде: `δ(q, a, z) = (r, α, t)` — из состояния `q` при чтении входного символа `a`
  (или `λ`) с верхушкой магазина `z` перейти в состояние `r`, заменить `z` на цепочку `α` в магазине и выдать цепочку
  `t` на выходную ленту.
- Обязательные элементы описания любого перевода в отчёте: (1) формальная спецификация СУ-схемы/преобразователя со всеми
  компонентами; (2) такт работы (`⊢`); (3) разбор (последовательность конфигураций) хотя бы одного контрольного примера.

### 2.5. Конфигурация и вывод МП-преобразователя (адаптация соглашений главы 3)

Программная часть работы (этап 3) — **универсальный МП-преобразователь**: все компоненты восьмёрки и правила `δ`
задаются json-файлом, входные строки-выражения читаются из консоли, каждый такт преобразования выводится в консоль.

Соглашения по наименованию:

- состояния преобразователя именуются в формате `q0, q1 … q5`;
- `Z` — начальный (нулевой) символ магазина; он всегда есть в магазине в начале работы преобразователя;
- конфигурация преобразователя — четвёрка, отображается в формате `(q1, abc, aZ, y)`, где `q1` — текущее состояние,
  `abc` — ещё не обработанная часть входной цепочки, `aZ` — текущее содержимое магазина (на вершине стека находится
  `a`), `y` — выходная цепочка, выданная к текущему моменту;
- пустая цепочка (вход, магазин, выход) обозначается `λ`;
- все сообщения в консоль выводятся на английском языке.

Формат вывода шагов работы преобразователя в консоль (каждый такт `⊢` — отдельная строка с порядковым номером,
нумерация начинается с `1` и своя для каждой входной строки):

```
1) (q0, abc, Z, λ) -> (q1, bc, aZ, a)
2) (q1, bc, aZ, a) -> (q2, c, Z, ab)
3) (q2, c, Z, ab) -> (qf, λ, λ, abc)
```

Формат json-файла с конфигурацией и правилами преобразователя:

- `states` — возможные состояния (`Q`);
- `inputAlphabet` — входной алфавит (`V`);
- `stackAlphabet` — алфавит магазина (`Z`);
- `outputAlphabet` — выходной алфавит (`V'`);
- `startState` — начальное состояние (`q₀`);
- `startStackSymbol` — начальный символ магазина (`z₀`);
- `finalStates` — заключительные состояния (`F`);
- `transitions` — правила `δ`; каждый элемент — объект с полями:
    - `state` — исходное состояние `q`;
    - `input` — входной символ `a` или `λ`;
    - `stackTop` — символ на вершине магазина `z`;
    - `newState` — новое состояние `r`;
    - `push` — цепочка `α`, заменяющая `z` в магазине (`λ` — удалить символ; тот же символ — не менять магазин);
    - `output` — цепочка `t`, выдаваемая на выходную ленту (`λ` — ничего не выдавать).

Что можно делать со стеком (показана только вершина стека):

1) добавить символ(ы): `Z` → `aZ`;
2) удалить символ: `a` → `λ`;
3) ничего не делать со стеком: `a` → `a`.

Пример json-файла (иллюстрирует только формат, а не требуемую таблицу `δ` для перевода в ОПЗ):

```json
{
  "states": ["q0", "q1", "q2", "qf"],
  "inputAlphabet": ["a", "b", "c"],
  "stackAlphabet": ["Z", "a"],
  "outputAlphabet": ["a", "b", "c"],
  "startState": "q0",
  "startStackSymbol": "Z",
  "finalStates": ["qf"],
  "transitions": [
    { "state": "q0", "input": "a", "stackTop": "Z", "newState": "q1", "push": "aZ", "output": "a" },
    { "state": "q1", "input": "b", "stackTop": "a", "newState": "q2", "push": "λ", "output": "b" },
    { "state": "q2", "input": "λ", "stackTop": "Z", "newState": "qf", "push": "λ", "output": "λ" }
  ]
}
```

Требования к конфигурации: детерминированность — для каждой тройки `(q, a, z)` должно существовать не более одного
правила; λ-правило для пары `(q, z)` допускается только при отсутствии правил по реальным входным символам для той же
пары; символы в `transitions` должны принадлежать заявленным алфавитам, `startState` и элементы `finalStates` —
множеству `states`, `startStackSymbol` — алфавиту магазина.

## 3. Предметное задание

### Этап 1. КС-грамматика и простая СУ-схема

1. Составить **КС-грамматику** для заданных арифметических выражений: операции `+`, `-`, `*`, `/`, целые числа, скобки.
   Грамматика должна задавать правильный приоритет операций (`*`, `/` выше, чем `+`, `-`) и левоассоциативность.
2. На её основе разработать **простую СУ-схему** для перевода в ОПЗ. Форма записи правил: `A → α,β` (входная часть,
   запятая, выходная часть).
3. **Выходные символы — терминалы `(num, +, -, *, /)` и пробелы**: числа переносятся в выходную ленту как лексемы `num`,
   операции — как свои символы, лексемы разделяются пробелами. Пример: вход `5 + 3* 2` → выход `5 3 * 2 +`.
4. Записать результат формирования в файл `.\lab-4\rules.md`.

### Этап 2. Построение МП-преобразователя

Для СУ-схемы перевода в ОПЗ построить **формальную спецификацию детерминированного МП-преобразователя**:

- определить множество состояний `Q`, входной алфавит `V`, алфавит магазина `Z`, выходной алфавит `V'`, начальное
  состояние `q₀`, начальный символ магазина `z₀`, множество заключительных состояний `F`;
- главное — определить **функцию переходов** `δ` (полный набор правил `δ(q, a, z) = (r, α, t)`);
- преобразователь должен считывать символы входной строки и записывать символы в выходную строку;
- привести такт работы (`⊢`) и полный разбор контрольного примера `5 + 3* 2` в виде последовательности конфигураций
  `(q, x, α, y)`.

Записать результат построенного автомата в файл `.\lab-4\rules.md`. Кроме того, подготовить json-файл с конфигурацией
и правилами построенного преобразователя (формат — п. 2.5), который будет использоваться программой на этапе 3
(например, `.\lab-4\transducer.json`).

### Этап 3. Программная реализация универсального МП-преобразователя

Реализовать **универсальный МП-преобразователь** — программу-интерпретатор, у которой конфигурация и правила
переходов не «зашиты» в код, а считываются из json-файла (формат — п. 2.5). Программа должна:

- при старте загрузить из json-файла (путь передаётся аргументом программы) конфигурацию и правила преобразователя
  и построить модель `P = (Q, V, Z, V', δ, q₀, z₀, F)`; сводку загруженного преобразователя (states, алфавиты, start,
  final, transitions) вывести в консоль;
- читать входные строки-выражения из **консольного ввода** в цикле (например, `5 + 3* 2`); условие завершения работы
  (пустая строка и/или служебная команда вроде `exit`) задокументировать в README;
- каждую введённую строку обрабатывать посимвольно, **имитируя такты МП-преобразователя** по правилам `δ`
  (состояние, магазин, выходная лента);
- **выводить в консоль каждый шаг преобразования** в формате из п. 2.5: `N) (q, x, α, y) -> (q', x', α', y')`;
- по завершении обработки строки вывести результат: ОПЗ-строку (для `5 + 3* 2` — `5 3 * 2 +`) и сообщение о принятии
  цепочки либо причину отказа;
- **корректно обрабатывать ошибки** (недопустимые символы, нарушение синтаксиса, дисбаланс скобок, недопустимые
  комбинации операций, ошибки конца входа и т.п., а также ошибки формата json-конфигурации) — с локализацией позиции
  ошибки и понятным сообщением; ошибка при обработке одной строки не должна завершать работу программы;
- для корректной работы преобразователя **реализовать λ-переходы** (переходы `δ(q, λ, z)`, выполняемые без чтения
  входного символа; в детерминированном преобразователе λ-переход разрешён только если для данного `q`, `z` нет
  конфликтующего перехода по реальному входному символу).

## 5. Требования к структуре решения

Рекомендуемая структура пакета (имена можно адаптировать, сохранив разделение ответственности):

1. **Модель преобразователя** — неизменяемое описание `P = (Q, V, Z, V', δ, q₀, z₀, F)`: состояния и символы —
   строковые идентификаторы (загружаются из json, а не «зашиты» в код как перечисления), тип
   `Transition(q, a, z) → (r, α, t)`, таблица переходов.
2. **Движок (интерпретатор) МП-преобразователя** — универсальный такт: по текущей конфигурации `(q, x, α, y)` и правилу
   из `δ` выполняет шаг `(q, ax, zγ, y) ⊢ (r, x, αγ, yt)`; поддерживает как переходы по чтению символа, так и
   λ-переходы; детерминирован — при неоднозначности (конфликте правил) сообщает об ошибке.
3. **Конфигурация конкретного преобразователя для ОПЗ** — json-файл (формат — п. 2.5) с фактическими множествами
   и таблицей `δ`, построенной по СУ-схеме из этапа 1; загрузчик на Jackson с валидацией, отображающий json в модель
   из п. 1.
4. **Ввод/вывод** — чтение конфигурации из json, консольный ввод строк-выражений, пошаговый вывод тактов в консоль
   (формат п. 2.5), вывод результата и диагностических сообщений.
5. **Обработка ошибок** — свои типы исключений (например, `TranslationException` с позицией символа,
   `ConfigurationException` для ошибок json-конфигурации), понятные сообщения; никакой вход не должен «ронять»
   программу необработанным исключением.

Порядок работы движка на каждом такте должен соответствовать формальному определению из п. 2.4 (состояние, оставшийся
вход, магазин, выходная лента) — это проверяется в тестах.

- **JUnit 5** как тестовый движок, **AssertJ** для утверждений (`assertThat(...)`), **Mockito** для изоляции
  зависимостей (например, подмена консольного ввода/вывода при проверке цикла чтения строк и пошагового вывода).
- Обязательные группы тестов:
    1. корректные выражения (движок работает с конфигурацией ОПЗ-преобразователя, загруженной из json-файла):
       `5 + 3* 2` → `5 3 * 2 +`; со скобками; все четыре операции; вложенные скобки; многозначные числа; выражение
       из одного числа;
    2. λ-переходы: сценарии, где такт выполняется без чтения символа (завершающие операции над стеком при конце входа);
    3. ошибки: недопустимый символ, `5 + * 3`, `5 +` (нехватка операнда), `(5 + 3` (дисбаланс скобок), `5 3 +`
       (недопустимая последовательность), пустая строка; проверяются код/сообщение и позиция ошибки;
    4. детерминированность и корректность такта: последовательности конфигураций для контрольного примера совпадают с
       ручным разбором из этапа 2; пошаговый вывод в консоль соответствует формату п. 2.5;
    5. парсинг json-конфигурации (Jackson): корректный файл; некорректный JSON; отсутствие обязательных полей
       (`states`, `startState`, `startStackSymbol`, `finalStates`, `transitions`); символы в переходах вне заявленных
       алфавитов; нарушение детерминированности (два правила с одинаковым `(q, a, z)` либо конфликт λ-правила
       с правилом по реальному символу для той же пары `(q, z)`);
- В тестах использовать параметрылизацию (`@ParameterizedTest`) для перебора выражений «вход → ожидаемая ОПЗ».
